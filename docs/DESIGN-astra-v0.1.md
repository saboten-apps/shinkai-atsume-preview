本アプリは、駿河湾の深海魚を毎日1種紹介し、図鑑収集とSNS投稿を通じて、沼津の実在する行き先への関心を育てる。ガチャの結果は日本時間の日付で決まり、全員共通とする。

魚の紹介と行き先の案内は、関係の強さを明示して掲載する。段階0ではエリアへの寄り道を提案し、段階1では協力店との「担当魚」という企画上の関係を紹介する。魚の展示・提供・入荷を推測して案内しない。

**段階0は、交渉を必要としない内容でローカル完成まで進める。**

| 段階 | 提供する体験 | 実装・運用の範囲 | 次へ進む条件 |
|---|---|---|---|
| 段階0：MVP | 今日の魚を引く、図鑑に集める、カードを保存する、エリアの公式情報・地図へ進む | 検証済み24種、4画面、端末内保存、画像生成、Threads用草稿、匿名集計用の計測処理 | ローカル検収完了。公開は控訴結果を確認し、公開方法を決めてから |
| 段階1：協力店 | 担当店を知る、来店スタンプを集める、合言葉・画面提示で来店を伝える | 店舗申請・承認、店舗情報更新、QR受付、店舗確認数の入力、月次報告 | 協力店の参加同意、更新担当、集計・フォーム基盤の準備 |
| 段階2：イベント・収益化 | 開催期間に合わせた特設カード・イベント図鑑 | イベント情報、専用の集計、掲載効果の検証。収益化の詳細は別途設計 | 実績が蓄積し、運用を継続できること。収益化の打ち出しは副業届完了後 |

初期設定は、仮称のまま開発、クイズ無効、店舗表示無効、イベント表示無効、外部計測送信無効とする。未決事項を理由に基礎実装を止めず、確定情報が必要な箇所は検収条件として管理する。

**デイリーガチャは、日本時間の日付と固定した抽選定義だけで決める。**

日付の境界は日本時間の午前0時とする。海外の端末でも、端末のタイムゾーン設定にかかわらず日本時間の日付を使う。

抽選は次の手順で行う。

1. 日本時間の日付を年月日の固定形式にする。
2. アプリ固有の固定文字列、抽選定義の版、日付を決められた順序で組み合わせる。
3. レア度選択用と魚選択用で識別文字列を変え、それぞれSHA-256で値を得る。
4. ハッシュの先頭4バイトを符号なし・ビッグエンディアンの整数として扱い、2の32乗で割って、0以上1未満の値にする。
5. 一方でレア度を選び、もう一方でそのレア度に属する魚を等確率で選ぶ。

魚の並び順は安定したIDの昇順とし、JSON内の記述順には依存させない。端末ID、所持状況、アクセス順、URL、公開先ドメインは抽選に使わない。

初期24種の構成と配分は、次を採用案とする。

| レア度 | 種数 | 日ごとの配分 | 同レア度内の1種あたり |
|---|---:|---:|---:|
| ★1 | 8種 | 40% | 5% |
| ★2 | 6種 | 25% | 約4.17% |
| ★3 | 5種 | 20% | 4% |
| ★4 | 3種 | 10% | 約3.33% |
| ★5 | 2種 | 5% | 2.5% |
| 合計 | 24種 | 100% | — |

レア度選択の区間は、順に0〜40%、40〜65%、65〜85%、85〜95%、95〜100%とし、境界は下端を含み、上端を含めない。

この配分は抽選上の重みであり、20日間に必ず1回★5が出るといった日程保証ではない。1日1種のため、最高レア度を極端に低くしてコンプを難しくしすぎない設計とする。また、レア度はゲーム内の出現頻度であり、生物学的な希少性や絶滅危険度を示さない。

初期24種のID・レア度・配分・抽選定義は確定後に固定する。説明文やイラストの修正では抽選結果を変えない。将来の追加魚は別シリーズとして扱い、初期図鑑の分母を変更しない。

**「引き直し不可」は、通常操作で同じ日の結果が変わらないこととして実装する。**

- 初回の「引く」操作で結果を表示し、その日の獲得記録を保存する。
- 同じ日の再訪、連打、再読み込み、別タブでは同じ魚を表示する。
- 保存データを削除しても、同じ日本時間の日付なら同じ魚が出る。
- 既所持の魚でも抽選をやり直さず、「すでに図鑑に登録済み」と表示する。
- 午前0時以降の次の操作から、新しい日の抽選を可能にする。
- 日付をまたいで演出や画像生成が完了した場合は、操作開始時に確定した結果日を保持する。
- 過去日の再抽選、取り逃した日の獲得、所持状況に応じた救済抽選はMVPに含めない。

バックエンドを持たない段階0では、端末時計の改変や保存データの編集を完全には防げない。「通常操作での結果固定」と「不正操作への耐性」を区別する。段階0の獲得記録を、金銭的な特典や厳密な来店証明に利用しない。

**図鑑は初期24種を独立したコレクションとして保存する。**

| 項目 | 仕様 |
|---|---|
| コンプ率 | 獲得済みの異なる魚ID数 ÷ 24。例：12／24種・50% |
| 重複 | コンプ率は増えない。獲得日が異なる場合のみ出会った回数を増やす |
| 記録 | 魚ID、結果日、抽選定義の版、初回獲得日を保存する |
| 日次記録 | 日付ごとに1件。同日の複数操作で件数を増やさない |
| 未所持 | 共通シルエットと「未発見」を表示する |
| コンプ後 | 達成表示を出し、その後も日替わりガチャとカード生成を継続できる |
| 来店スタンプ | 段階1の別記録。魚の獲得数・コンプ率には加算しない |
| 追加シリーズ | 初期24種とは別の分母・達成状態で管理する |

全員が同じ魚を引くため、個人別の順位や「他の人より運がよい」といった演出は採用しない。

コンプに必要な日数は保証しない。初期データ確定後、連続した365日分の結果を検査し、24種すべてが登場することと、出現間隔に問題がないことを確認する。これは予定表の検品であり、毎日開かない利用者のコンプを保証するものではない。

保存できない環境では、今日の結果と行き先は利用可能にし、「この環境では図鑑を保存できません」と表示する。保存失敗を成功として扱わない。

公開先変更に備え、図鑑画面には利用者操作によるバックアップ出力・復元を設ける。復元対象は獲得記録と設定で、同じ日付の記録は重複加算しない。自動同期やアカウント登録は設けない。localhostから公開先へ履歴が自動移行することもない。

**fish.jsonには、公開可能な検証済みデータだけを収録する。**

最上位に、構造の版を示す`schema_version`、内容改訂を示す`catalog_version`、初期図鑑を識別する`collection_id`、魚の配列`fish`を持たせる。抽選に関わる固定情報は、別の抽選定義として管理する。

| フィールド | 型・必須性 | 内容・制約 |
|---|---|---|
| `id` | 文字列・必須 | 一意で変更しないASCIIのID。名前の修正でも変更しない |
| `name` | 文字列・必須 | 裏取りした和名。同名異種を避ける |
| `scientific_name` | 文字列・必須 | 対象種の同定に使う学名。根拠資料を必要とする |
| `rarity` | 整数・必須 | 1〜5。ゲーム内設定 |
| `depth_m` | オブジェクト・必須 | 下限`min`、上限`max`、必要な限定表現`qualifier`。単位はm |
| `fact` | 文字列・必須 | うんちく1文。カード用に原則52文字以内。短くしても事実の条件を落とさない |
| `fact_source_url` | URL・必須 | うんちくの内容を直接確認できる出典 |
| `area_hint` | エリアID・必須 | 行き先定義への参照。魚の展示・提供場所を意味しない |
| `illustration_file` | 相対パス・必須 | 同梱画像。外部画像の直接読み込みは行わない |
| `illustration_alt` | 文字列・必須 | 視覚的特徴を説明する代替テキスト |
| `accent_color` | 色コード・必須 | 統一された背景上で使う魚ごとのアクセント色 |
| `evidence` | 配列・必須 | 各事実項目と出典の対応 |
| `verification` | オブジェクト・必須 | 検証状態、確認日、確認担当、確認記録ID |
| `quiz` | オブジェクト・任意 | 問題、選択肢、正解、解説、出典、検証状態。初期は無効 |

`depth_m`は、資料で確認できない下限・上限を推測して補わない。片側だけ確認できる場合は、もう片側を未設定にし、「最大約○m」など根拠に合う表現を使う。両側とも不明な魚は初期投入対象から外す。単発の漁獲深度を、その魚の生息範囲に読み替えない。

`evidence`の各要素には、対象項目、出典URL、資料名、発行主体、確認日、確認内容のメモを持たせる。少なくとも次を確認する。

- 和名と学名が対象種に一致すること。
- 生息水深の表現が根拠資料に対応すること。
- うんちくの主語・条件・数値が正しいこと。
- 駿河湾との関係を確認できること。
- 食用・展示に触れる場合、その事実を別途確認できること。

`fact_source_url`だけで、名前・水深・駿河湾での記録まで裏取り済みとは扱わない。うんちくのURLは、`evidence`内の対応する出典と一致させる。

**魚データの投入には、機械検査とMuseの内容確認の両方を必要とする。**

1. 調査中の候補は、配信用データとは別の下書きとして保管する。
2. 博物館、水族館、研究機関、論文など、該当種と記述内容を確認できる資料を優先する。
3. Museが出典本文を確認し、魚・項目・出典の対応を承認する。
4. 必須項目、URL形式、ID重複、水深の大小関係、画像参照、文字数、検証状態を機械検査する。
5. 検証状態が承認済みのレコードだけを、配信用fish.jsonへ出力する。

URLが開けることだけでは内容の正しさを確認できない。AIが生成した説明文も、根拠確認前は未検証として扱う。

24種が揃わない場合、未検証データで穴埋めしない。実装はテスト専用の擬似データで進められるが、擬似データは配信用成果物から除外する。初期種数を減らす場合は、配分と図鑑の分母を含む仕様変更としてMuseが管理する。

公開後に疑義が生じた情報は、カード・画像・投稿文への出力を停止する。抽選結果IDを別の魚へ差し替えず、「情報を確認中」と表示し、再検証後に復帰させる。誤情報を含む過去の生成物についても、運用側で訂正の必要性を確認する。

**エリアの案内は、魚データから独立して更新できるようにする。**

行き先は`areas.json`相当の定義で管理する。

| 項目 | 内容 |
|---|---|
| エリアID・名称 | 例：沼津港エリア。名称を確認して登録する |
| 案内文 | 地域の回遊を促す文章。魚の展示・提供を断定しない |
| 公式案内URL | エリア・施設等の公式情報へのリンク |
| 地図検索URL | エリア名によるGoogleマップ検索へのリンク |
| 最終確認日・有効期限 | 初期運用案は90日ごとの確認 |
| 表示状態 | 有効、確認待ち、停止 |

リンク先が未確認、期限切れ、停止中の場合は、そのリンクを表示しない。未確認の別リンクへ自動で置き換えない。

段階0では、特定店舗のロゴや担当店表示は使わず、エリア名と公式情報・地図検索を案内する。

**shop.jsonは、段階1の承認済み店舗情報を表示するためのデータとする。**

最上位に`schema_version`、更新日時、店舗配列`shops`を持たせる。店側フォームの生データをそのまま公開せず、承認済み情報から生成する。

| フィールド | 型・必須性 | 内容・制約 |
|---|---|---|
| `id` | 文字列・必須 | 一意で変更しない店舗ID |
| `name` | 文字列・必須 | 店舗が確認した掲載名 |
| `status` | 列挙値・必須 | 有効、一時停止、掲載終了 |
| `assigned_fish_id` | 魚ID・必須 | 1店舗につき担当魚1種 |
| `area_id` | エリアID・必須 | 所属エリア |
| `address_public` | 文字列・必須 | 公開可能な所在地 |
| `official_instagram_url` | URL・必須 | 店舗の公式Instagram |
| `map_url` | URL・必須 | 店舗を特定できる地図リンク |
| `official_url` | URL・任意 | 公式サイト等 |
| `invitation_text` | 文字列・必須 | 来店案内文。担当魚の提供・展示を推測しない |
| `information_source_urls` | URL配列・必須 | 店舗情報の確認元 |
| `participation` | オブジェクト・必須 | 掲載同意日、参加開始日、終了日があればその日 |
| `freshness` | オブジェクト・必須 | 最終確認日、有効期限 |
| `stamp_campaign_id` | 文字列・任意 | スタンプ企画の公開識別子 |
| `approved_revision` | 文字列・必須 | 承認済み更新の識別子 |

連絡担当者、連絡先、申請本文、承認メモ、編集用トークン、QR検証用の秘密情報はshop.jsonに含めない。

1店舗は1種を担当し、同じ魚を複数店舗が担当することは許容する。複数店がある場合、画面では一覧を表示し、カードで紹介する1店は日付による固定ローテーションで選ぶ。初期段階に有料優先枠は設けない。

担当魚との関係は企画上のものとし、「担当魚だから食べられる」「担当魚だから展示されている」と解釈させない。

店舗情報は、初期運用案として30日ごとに店側へ確認を求める。有効期限を過ぎた店舗は行き先候補から外し、エリア案内へ戻す。営業時間や入荷情報を恒常的に転記する運用は避け、最新情報は公式案内へ誘導する。

店側の登録・修正は、次の流れとする。

1. 店側がフォームから登録・修正を申請する。
2. 入力形式や必須リンクを自動検査する。
3. Museが変更点、根拠、掲載表現を確認して承認する。
4. 承認済み情報からshop.jsonを更新する。

修正申請中は、既存の承認済み情報を表示する。閉店、掲載辞退、誤掲載は即時停止できるようにする。店側フォーム、編集権限、承認処理のための保存先・APIは段階1で追加する。

**結果カードは、魚の紹介を上半分、行き先の提案を下半分に配置する。**

標準画像は1080×1350px、縦横比4:5、PNG、透過なしとする。画面表示は縮小プレビューにし、保存画像は同じ原寸で生成する。

左右の安全余白は64pxとする。

| 縦位置 | 要素 | レイアウト |
|---|---|---|
| 0〜96px | アプリ名・結果日 | 上部に小さく配置。日付を必ず残す |
| 96〜352px | 魚イラスト | 中央配置。縦横比を維持し、魚体を切らない |
| 352〜464px | 魚名 | 最大2行。標準48px程度 |
| 464〜512px | レア度・生息水深 | 星と数値・文字を併記する |
| 512〜632px | 一言うんちく | 原則2行。標準34px程度 |
| 632〜680px | 出典表示 | 出典の短縮名を表示。詳細URLはアプリに掲載 |
| 680〜1184px | 行き先欄 | 「今日の寄り道ヒント」、エリア名、案内文、公式情報・地図への誘導 |
| 1184〜1350px | 注意文・運営名 | 展示・提供の条件、うみまちラボ沼津の名称 |

長文を小さな文字で押し込まず、収まらないデータは編集へ戻す。魚名、限定条件、出典を省略して意味を変えない。

段階0の行き先欄は、次の文言を基本とする。

- 見出し：「今日の寄り道ヒント」
- エリア名：「沼津港エリア」
- 案内：「深海の世界や港のまちを楽しむきっかけに。」
- 誘導：「公式情報・地図はアプリの行き先欄へ」
- 注意：「魚の提供・展示は各施設の当日の状況によります。」

画像内の誘導文は、押せるボタンのようには描かない。実際のリンクはアプリ画面に置く。

段階1では、承認済みかつ有効な店舗について、「この魚の担当店」と店舗名を表示できる。その際は「担当は企画上のものです。展示・提供状況は公式案内をご確認ください」と添える。店舗情報が期限切れの場合は、エリア版を生成する。

| 使用できる表現 | 使用しない表現 |
|---|---|
| 「沼津港エリアをめぐるヒントに」 | 「今日、沼津港でこの魚が食べられます」 |
| 「深海の展示情報を公式サイトで確認」 | 「この魚に必ず会えます」 |
| 「○○店は、この魚の担当店です」 | 「担当店でこの魚を提供中です」 |
| 「港エリアの食を楽しもう」 | 未確認の「旬」「入荷中」「名物」「おすすめ料理」 |

画像生成は、画面表示と同じ検証済みデータを使う。画像と日本語フォントの読み込み完了後に描画し、未完成の画像を保存させない。素材とフォントは同梱し、外部画像の読み込み制約や外部フォント障害に依存させない。

当日の魚は「今日の深海魚」、過去の魚を詳細画面から再出力する場合は「図鑑カード」と獲得日を表示する。古い結果を「今日の魚」として出力しない。再生成時の行き先は、その時点で有効な情報を使う。

共有機能が利用できる環境では画像共有を使い、それ以外ではPNG保存と文章コピーを提供する。画像共有・保存から、SNSへの投稿完了を推定しない。

**イラストは、24種を並べたときに同じ企画として見える様式に統一する。**

深海の暗い背景、限定した発光アクセント、魚ごとの色コードを共通ルールとする。魚体の向き、背景色、光源、線や質感の密度、余白を制作見本で固定する。

原画は横長2:1を基本にし、文字や星、店舗情報は描き込まない。合成時に魚体が切れない構図とする。

生成後はMuseが、ひれの位置、体形、口や眼など識別に関わる特徴を資料と照合する。装飾的な発光を、生物が実際に発光する性質として誤解させない。制作記録には使用した様式の版と確認結果を残す。

**公開側の画面は、SPECの4画面を維持する。**

| 画面 | 主な要素 | 操作・遷移 |
|---|---|---|
| 1. トップ／今日のガチャ | 日本時間の日付、未実行時の「引く」、実行後の魚カード、出典、行き先、画像保存、投稿文コピー | ガチャ実行、魚詳細、図鑑、外部リンクへ |
| 2. 図鑑 | 獲得数・24種、コンプ率、魚グリッド、未所持シルエット、バックアップ・復元 | 所持魚から魚詳細へ。未所持は「毎日のガチャで発見」を案内 |
| 3. 魚詳細 | 魚名、イラスト、レア度、水深、うんちく、各出典、獲得日、カード再生成、行き先 | 図鑑へ戻る、外部リンク、画像保存 |
| 4. このアプリについて | コンセプト、運営者、データ・イラストの扱い、出典方針、保存・計測の説明、免責 | トップへ戻る |

基本ナビゲーションは「今日」「図鑑」「このアプリについて」の3項目とし、魚詳細はトップと図鑑から開く。

トップには、未実行、抽選演出中、結果表示、保存失敗、データ確認中の状態を設ける。演出中の連打では処理を増やさない。動きを抑える設定に対応し、演出を省いても同じ結果を得られるようにする。

魚詳細のURLを直接開いても獲得扱いにしない。未所持・存在しないIDへのアクセスでは、情報の誤表示や記録の追加を行わない。

操作はキーボードでも行え、星や色だけに情報を依存させない。画像には代替テキストを付け、狭い画面でも名前・注意文・出典リンクが欠けないことを検収する。

免責には、次の文言を掲載する。

「魚の提供・展示は各施設の当日の状況によります。最新情報は各施設・店舗の公式案内をご確認ください。」

**段階0の計測は、行き先への関心を数字にし、来店数とは区別する。**

静的ファイルとlocalStorageだけでは、全利用者のアクセスやクリックを集約できない。そのため、表示・抽選・保存と、計測の送信先を切り離す。

現在はローカル用の計測先を使い、イベントの記録と集計出力を検証する。公開方法を決めた段階で、ホスティング側の機能または外部の集計基盤へ接続する。段階0ではアプリ専用のデータベースや業務APIを持たない構成を基本とする。

計測基盤を一切使わない場合は、全体のクリック集計を実現できない。その状態を「計測実装済み」とは扱わない。

| イベント | 発火条件 | 主な用途 |
|---|---|---|
| ページ表示 | 画面への遷移時。内部の再描画では増やさない | アクセス集計 |
| 結果カード表示 | 結果カードが表示されたとき | 行き先への誘導機会の把握 |
| 行き先クリック | 公式情報・地図等への実際のクリック | エリア・店舗への関心の把握 |

送信項目は、イベント種別、日付、画面種別、魚ID、エリアID、段階1以降の店舗ID、リンク種別、掲載位置、必要な企画IDに限定する。集計日は日本時間とし、過去の魚カードからのクリックでも、クリックした日の件数として扱う。

氏名、メールアドレス、位置情報、図鑑履歴、永続的な端末IDは送信しない。自由入力文や完全な閲覧URLも送信項目に含めない。

通信上は受信側にIPアドレス等が伝わるため、集計先のアクセスログも含めて保存方針を確認する。「個人情報を一切扱わない」と無条件には表示せず、実際の構成に沿って説明する。

計測送信が失敗しても、行き先リンクは開く。通信失敗や遮断による欠測を許容し、「計測できた範囲の件数」として扱う。

段階0で返せる数字は、例えば次の形になる。

| 指標 | 報告内容 |
|---|---|
| エリア別クリック数 | 沼津港エリアへのクリック総数 |
| リンク別内訳 | 公式案内と地図検索のそれぞれの件数 |
| 掲載位置別内訳 | トップと魚詳細からの件数 |
| 誘導機会との比較 | 結果カード100表示あたりの行き先クリック件数 |

これらは人数、実来店数、売上ではない。複数回のクリックを含むため、ユニーク来訪者数や来店率として表示しない。また、段階0のエリアクリックを、後から参加した特定店舗の実績として割り当てない。

**段階1では、店舗が確認した来店とQRの受け取りをそれぞれ報告する。**

来店確認は、店舗で無理なく続けられることを優先する。

| 方法 | 店側の操作 | 記録単位 |
|---|---|---|
| 合言葉 | 来店時に合言葉を確認し、日次フォームへ件数を入力する | 来店1組につき1回 |
| 画面提示 | アプリ画面を確認し、合言葉とは別の欄へ入力する | 合言葉で数えていない来店1組につき1回 |
| 店頭QR | 来店者がQRを読み取り、スタンプを受け取る | QR受取件数。同一端末・同一店・同日は通常操作で1回 |

同じ来店で合言葉と画面提示の両方があった場合は、合言葉側だけに数える。この運用ルールを店側フォームに明記する。

QRスタンプは、担当魚の図鑑枠に付く来店記録とする。未所持の魚の枠にも付けられるが、魚そのものを獲得したことにはしない。ガチャの24種コンプ率は変えない。

QRには店舗・企画に対応する受付情報を持たせ、段階1の検証APIで参加状態と有効性を確認する。検証用の秘密情報を静的ファイルに埋め込まない。同じ受付の再送信で件数を増やさず、成功した受領記録だけを端末に保存する。

通信できない場合は未確定として表示する。検証に成功していないスタンプを、取得済みとして扱わない。

常設QRは写真やURLを共有できるため、読み取りだけで実来店を完全には証明できない。QR受取件数は参考指標とし、店舗確認の来店組数と合算しない。より厳密な証明が必要になった場合は、店舗が渡す使い切りコード等を別途設計する。

月次報告は、店舗ごとに対象月、掲載日数、掲載停止期間、情報確認日、計測できた範囲を添える。以下は形式を示す架空の例である。

| 指標 | 例 | 店舗への説明 |
|---|---:|---|
| 店舗付きカード表示 | 120回 | 店舗情報が表示された回数 |
| 店舗の公式リンククリック | 18回 | 公式情報へ進んだ操作数 |
| 店舗の地図クリック | 12回 | 地図へ進んだ操作数 |
| 合言葉確認 | 7組 | 店舗が確認・申告した来店組数 |
| 画面提示のみ確認 | 3組 | 合言葉との重複を除いた来店組数 |
| 店舗確認の合計 | 10組 | 上記7組と3組の合計 |
| QR受取 | 8件 | 来店確認との重複が不明な参考値 |

この例を「18組来店」とは報告しない。店舗確認10組とQR8件の重複を判断できないためである。また、店舗確認数から「純増客」「広告による売上」を推定しない。

帳票はCSVと閲覧用の形式で出力し、Museが確認して店舗へ渡せるようにする。店舗には自店の集計を返し、他店の個別実績は含めない。

**Threads用には、画像・本文・1stリプライを別々に用意する。**

| 頻度・契機 | アプリが用意する出力 | 確認点 |
|---|---|---|
| 毎日 | 今日のカードPNG、本文草稿、質問、画像の代替テキスト、1stリプライ用リンク | 魚・日付・事実・リンクの一致 |
| 週1 | 直近7日間の登場魚、レア度のまとめ、運営端末の図鑑獲得数 | 重複魚と獲得数の扱い |
| 担当店追加時 | 店舗紹介カード、担当魚との関係を説明する草稿、公式Instagram・地図 | 店舗の承認、掲載期間、提供・展示を断定していないこと |
| イベント時 | 開催日・場所を明記したカードと草稿 | 開催期間、変更・中止情報 |

毎日の本文は、魚名、一言うんちく、地域への誘い、質問の順を基本とする。出典名は本文にも含められるようにし、URLは1stリプライ側にまとめる。

質問の初期候補は「見たことある？」「どこが気になる？」などとする。「食べたことある？」は、その種の食用に関する裏取りが済み、誤解のない文脈で使える場合だけ候補に出す。

図鑑は端末内保存なので、全利用者の平均コンプ率を算出しない。週次投稿のコンプ率には「運営端末の図鑑」など、誰の記録かを明示する。

公開URLが未設定の間は、アプリへのリンクを空欄にし、運用側に未設定と表示する。localhostのURLや架空の公開URLを投稿用リンクとして出さない。出典・行き先の確認済みURLは、必要に応じて1stリプライの草稿に含める。

日次・週次の出力は草稿であり、自動投稿しない。Museの検品を経て、投稿者本人が事前確認して手動投稿する。

**ローカル開発は、公開先を決めなくても完成・検収できる構成にする。**

実装はViteとTypeScriptによる静的フロントエンドを採用案とする。開発時はローカルHTTPサーバーで動かし、配信用成果物は静的ファイルとして生成する。

内部は次の責務に分ける。

| 責務 | 内容 |
|---|---|
| 日付・抽選 | 日本時間の日付、固定抽選、結果日の保持 |
| データ検証 | スキーマ、出典項目、検証状態、参照整合性 |
| 図鑑保存 | 日次記録、コンプ率、バックアップ、復元 |
| 表示用データ生成 | 画面・カード・投稿文で共通利用する情報 |
| 画像生成 | Canvas描画、文字配置、画像保存 |
| 計測 | ローカル記録と公開後の集計先への接続 |
| 店舗・スタンプ | 段階1で追加する承認済みデータとAPI接続 |

ルーティングはハッシュ方式を基本とし、特定ホストのURL書き換え機能を必須にしない。画像・データの参照は配置先に対応できる相対パスとする。

公開URL、計測先、店舗機能の有効・無効は設定として切り替える。抽選結果はこれらの設定に依存させない。

開発資産は当面Muse VMのworkspaceで管理し、ローカルの変更履歴とバックアップを残す。GitHubへの接続を、開発・起動・検収の必須条件にしない。控訴結果を確認した後に、リポジトリ移管と公開方法を決める。

初期表示では必要な画像だけを読み込み、図鑑の画像は遅延読み込みする。無料枠への対策として転送量と計測件数を確認するが、利用するサービスが未確定の段階で無料運用を保証しない。

**段階2のイベントは、通常のデイリーガチャから独立させる。**

イベントデータには、企画ID、名称、開始・終了日時、会場、参加店舗、担当魚、公式情報URL、確認日、表示状態を持たせる。

通常の今日の魚は変更せず、イベント用カード・スタンプ・図鑑を別枠で表示する。イベント参加によって同じ日の通常ガチャを引き直せるようにはしない。

終了したイベントは通常の行き先候補から外し、過去情報には開催日を明記する。収益化は副業届完了後に検討し、それまでは無料掲載で掲載効果と運用負荷を確認する。有料プラン、決済、優先掲載の詳細は、このMVPでは確定しない。

**リスクは、データ・案内・計測・継続運用の観点で管理する。**

| リスク | 影響 | 対応 |
|---|---|---|
| 魚情報の誤り、別種との混同 | 企画・運営者への信頼を損なう | 項目ごとの出典、学名による同定、Museの承認、疑義発生時の出力停止 |
| イラストの不統一・形態の誤り | 図鑑としての品質が下がる | 共通見本と制作条件を固定し、24種を並べて検品する |
| 展示・提供しているとの誤解 | 無駄な来訪や店舗への問い合わせにつながる | 行き先の意味を明記し、カード・画面・投稿すべてで断定表現を避ける |
| 店舗・エリア情報の陳腐化 | 閉店先や無効リンクへ案内する | 確認日と有効期限、店側修正フォーム、即時停止、エリアへの復帰 |
| コンプまでの長さ・重複の多さ | 継続利用が落ちる | 初期配分と年間予定表を検品し、コンプ日数を保証しない |
| 端末時計・保存データの変更 | 不正な獲得記録を作れる | 段階0の記録を厳密な証明に使わない。QR受付は段階1で検証する |
| 保存領域の消去・公開先変更 | 図鑑が失われる | 保存範囲を説明し、利用者操作のバックアップ・復元を用意する |
| クリック数の過大解釈 | 実績説明が不正確になる | 件数・組数・参考値を明記し、来店・売上に換算しない |
| QRの共有・再取得 | 受取件数が来店数より大きくなる | QRを来店証明と断定せず、店舗確認数を別途集める |
| 無料枠・サービス仕様の制約 | 計測停止、受付停止、費用発生 | 公開前に枠と上限時の挙動を確認し、画像を軽量化する。停止中の欠測を明示する |
| 店舗側の入力負担 | 来店集計が継続しない | 日次の少数項目に絞り、入力にかかる時間も試験運用で確認する |
| GitHub控訴の長期化 | 公開方法を決められない | ローカル開発を継続し、公開先固有の機能に依存させない |
| 古い共有画像が残る | 修正前の情報が流通し続ける | 日付を画像に残し、現在の案内はアプリ・公式情報で確認できるようにする |

===== 要約 =====

- **コンセプト**：毎日みんなに同じ深海魚が出るガチャを入口に、図鑑収集・Threads投稿・沼津のお店めぐりをつなぐ。
- **MVP機能**：裏取り済み24種、日付固定ガチャ、端末内図鑑、SNSカード、エリア案内、投稿草稿、クリック計測の仕組み。まずローカルで完成させる。
- **集客の核**：毎日の魚カードから行き先へ誘導し、段階1では担当店・来店スタンプ・合言葉へ発展させる。クリック数と店舗確認の来店組数は区別して返す。
- **最大のリスク**：魚情報の誤りと、「その魚を店で食べられる・見られる」という誤解。出典必須、未検証データ禁止、断定しない文言で抑える。
- **未決事項**：正式名称、24種のリスト、クイズ、イラスト様式、最初の協力店、集計基盤。公開方法はGitHub控訴の結果を確認してから決める。
