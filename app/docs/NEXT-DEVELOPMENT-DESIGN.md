# 深海あつめ：これからの開発設計

作成日: 2026-11-15。対象: React / Three.js の既存アプリ。
本書は今回の設計成果物であり、以下の新機能は未実装。既存状態は [ASTRA-HANDOFF.md](./ASTRA-HANDOFF.md)、実装担当への指示は [AI-HANDOFF.md](./AI-HANDOFF.md) を参照。

## 1. 目指す体験と判断基準

「今日の魚を引く → 沼津を飛ぶ・歩く → 魚や街の発見を持ち帰る」を入口にし、地域の人が自分の街を見せたくなるアプリへ育てる。
当面の成果は、うみまちラボの認知と、街の人からの具体的な感想・写真提供。最終的なAI導入支援の仕事への接点は長期目的であり、ゲーム画面を営業資料にしない。

次の開発では、範囲をさらに広げるより、**一棟を選べる、一棟を直せる、直した場所を共有できる**ことを優先する。画質の改善と地域参加を同じ更新の仕組みで支える。

判断基準:
- Pixel 10 Proで街歩きと探索が快適である。
- ガチャを開いた時の軽さと既存の図鑑を守る。
- 更新した建物を、写真と見比べて確認できる。
- 写真が集まるほど更新作業を再利用できる。
- 維持費と手作業が個人運営の範囲に収まる。

## 2. 決定済み・事実・今回の提案

### 決定済み
- ガチャと3Dは一つのアプリ。入口はガチャ。2D代替を維持する。
- 本番は shinkai-atsume、テスト公開は shinkai-atsume-preview。
- 自前写真で主要建造物を改善したい。ダウンロードと描画の軽さを重視する。
- 地域の希望者に写真や紹介リンクを提供してもらう構想がある。
- 現状はサーバー・アカウント・同時プレイなし。営業や外部連絡の代行は依頼されていない。

### 確認できている現状
- 建物は2023年度LOD3配布セット。56区画、20,522建物レコード。全棟が写真付き・高精細ではない。
- 道路・植生は2023年度、地形・水面は2021年度。年度をひとまとめに表示しない。
- 原本にはgml_idがあるが、現在の描画用GLBでは建物との対応を保持していない。
- 市役所は個別の軽量モデルとユーザー写真で改善済み。びゅうおの個別改修は未実装。
- 事前保存は実装済み。既存の保存対象は約70.8MB。完全オフラインアプリではない。
- ユーザーから「軽い」との感想あり。Pixelの定量測定は未実施。

### 今回の推奨設計（未実装）
- 管理用の建物選択、版付きの建物修正台帳、一区画からの展開。
- びゅうおを次の近景改善の試作対象にする。
- 地域紹介は掲載内容を確認できた1件から手動運用。
- 公開投稿システムより先に、紹介画面と更新作業を完成させる。

## 3. データ構成：元の街と修正を分ける

基本構成は `公開元データ → 変換 → 区画GLB + 選択情報 → 修正適用 → 配信`。
写真の出所と確認日は修正台帳で管理し、地図の年度更新時にも独立して残す。
新しいPLATEAUに入れ替えた場合は修正との競合を確認する。古い修正を無条件に新しい建物へ当てない。

### エンティティ案

| 種類 | 管理する情報 | 意味 |
|---|---|---|
| SourceBuildingRef | 提供元、年度、データセット、タイル、gml_id | その版の原本建物を識別 |
| BuildingRecord | 独自buildingKey、複数のSourceBuildingRef、位置、外形、対応確認状態 | 年度をまたぐ建物の管理単位 |
| PlaceRecord | 独自placeId、buildingKey、入口位置、紹介文、リンク、掲載確認状態 | 店舗・施設の紹介。1建物に複数可 |
| BuildingOverride | overrideId、buildingKey、対象の原本版、操作、アセット、根拠、確認日、revision | 見た目・形状の修正 |
| AssetRecord | assetId、ファイル、hash、容量、作者、利用条件、撮影日、クレジット | 公開素材の由来と版 |

buildingKeyはアプリ側の建物ID、placeIdは店舗等のID。建て替え後は原則別buildingKeyにし、必要なら旧建物への関係を記録する。移転した店舗のplaceIdと所在地履歴は分離する。
座標はWGS84の緯度経度を交換用に持ち、描画時に既存ENUへ変換する。高さの基準と、元の高さ／表示倍率適用後の高さを明記する。

### 修正操作

| 現実の変化 | 操作案 | 実装上の注意 |
|---|---|---|
| 外壁の塗り替え | appearance | その建物の面だけ変更。他の建物と共有する材質全体を変えない |
| 古い粗い形状を精細化 | replace | 元形状・元衝突を除き、置換形状・衝突を登録 |
| 解体 | hide | 描画と衝突の両方から除外。必要なら地面も修正 |
| 新築・元データにない建物 | add | 新しい独自ID、配置、衝突、LOD、出典を定義 |
| 店舗の入れ替わり | PlaceRecord更新 | 建物の外形を変えず紹介情報だけ更新 |

修正データは `draft → verified → published → retired` の状態を持たせる。初期版はGit上のJSONと人手レビューでよく、管理画面やデータベースは不要。
内部用の連絡先・同意原文・元写真GPSを公開JSONに含めない。配信時に公開用フィールドだけ出力する。

### 適用方法の推奨

初期のhide/replaceは**原本の建物IDで対象面を除外して区画を再生成**し、置換モデルを別アセットとして読む方式を優先する。区画全体を非表示にしたり、地下へ押し込んだりしない。
appearanceも同じIDで対象面を分離し、UVと材質の対応を確認する。高解像度の写真を貼るだけでは粗い輪郭は改善しない。
ランタイムで元建物を隠す方式は、ID対応と衝突更新を確実に保てると検証できた場合のみ採用する。
近景専用モデルには中遠景の軽量モデルを用意し、切替時の二重描画・消失・衝突のずれを検証する。
市役所の既存の特別処理は、最初から全面書き換えず、新方式の置換が検証できてから移す。

### 年度更新と競合

1. 新旧データの収録範囲・ID・形状・容量の差分を生成。
2. ID、位置、平面形状の重なり等で対応候補を作る。距離だけで自動確定しない。
3. 一対多・多対一・解体・新築・不一致を要確認にする。
4. 新版で既に修正済みなら独自修正を廃止。未解決の修正がある区画は旧版を維持する。
5. 修正と原本の組合せが検証された版を公開する。

## 4. 建物選択を先に実証する

対象は一区画、隣り合う建物・細長い建物・高さの違う建物を含む最低10件。
候補はA:圧縮後にも残るfeature属性、B:原本由来の選択形状と空間索引のsidecar。
両方を全域実装せず、小さなデータで比較して一方を選ぶ。平面外形だけで曖昧な重なりを無理に確定しない。

必須条件:
- 屋根・壁を選ぶと原本と同じIDを得る。
- gltfpack後のfaceIndexを圧縮前の索引に直接対応させない。
- 1.3倍の高さと市役所の置換に選択位置が合う。
- 区画再読込後もIDが同じ。選択データも区画と一緒に解放する。
- 20,000個のMeshを増やす方式を避ける。操作前後のdraw call、メモリ、フレーム時間を記録する。

初期UIは明示的な管理用選択モード。通常の飛行操作ではタップ自動飛行等と競合させない。
カードに建物ID・緯度経度・データ年度・「情報をコピー」を表示する。技術IDは一般利用者向けの画面に常時表示しない。

## 5. 写真から近景を改善する手順

最初の対象はびゅうお。市役所の写真適用を既存の比較対象にする。
元写真は既に `/workspace/shared/numazu-originals/` に16枚取得済み。ZIPの再送を求めない。

1. 同じ位置・視野角で現状のスクリーンショットを保存する。
2. 写真に見える塔、展望通路、水門扉、外階段を分け、現状との差を列挙する。
3. 写真で確認できる形だけ軽量モデルにする。寸法の推定部分と未撮影面を記録する。
4. 外壁・窓枠・手すりを、形状で必要な部分と写真で表現できる部分に分ける。
5. 昼写真を基本の色に使い、夜の照明色を恒常的な外壁色として焼き込まない。
6. 立ち位置を固定して改善前後を比較し、徒歩・飛行・中遠景を確認する。

不足写真だけ、対象面・撮る理由・位置の目安を付けて依頼する。写っていない面を「実写再現済み」としない。
初期の追加配信予算は、1ランドマーク圧縮後3MB以下を目安とする**提案値**。超える場合は、効果と実機計測を比較して調整する。
近景モデルのtriangles、draw call、GPUテクスチャ推定量も記録する。画像ファイルのMBだけで軽さを判定しない。

## 6. 地域参加と紹介画面

初期の参加ループは「ユーザーが街を見せる → 希望者から写真・情報を受け取る → 内容を確認 → 一棟を更新 → 更新した場所を共有」。自動公開しない。
写真提供の有無と、店舗紹介の掲載希望は別に確認する。建物が描画されているだけで協力店扱いしない。

紹介画面は探索を塞がないボトムシートとし、名称・短文・写真1枚・公式リンク・情報確認日を表示。閉じると元の位置へ戻れる。
紹介は明示的なマーカーから開く。建物選択の技術UIと分ける。
未紹介の建物をタップして大量の空カードが出る体験は避ける。
実在の営業時間や営業状態を推測しない。外部リンクはhttp/httpsのみとし、HTMLをそのまま描画しない。

共有はplaceIdを含むURLと、任意の景色カードを候補にする。URLを開くと軽い紹介を先に表示し、「街で見る」で3Dを読む。未ガチャの閲覧者に今日の魚の取得を与えない。
掲載終了・リンク変更・写真差し替えを同じ台帳で行えるようにする。最初は1件、次に3〜5件で運用負担を確かめる。
希望者の素材がない場合は架空の公開店舗データを作らず、ローカル専用の明示的なテストデータでUIを検証する。

## 7. ダウンロードと性能

既存の保存機能を維持し、選択sidecar・修正manifest・近景モデルも保存対象の参照関係へ組み込む。
原本・修正・選択データの組合せをreleaseIdで固定する。新旧のID表や衝突形状を混在させない。
必要アセットの検証が終わってから新しい版へ切り替える。失敗時に動作中の版を消さない。
削除するキャッシュを地図専用に限定し、ガチャ/図鑑保存に触れない。

第1段階は既存の全街保存UIを維持。素材が増えた時点で「基本の街／高精細の場所／地区別」の任意保存を追加する。
地区別保存はタイルや共有アセットの参照数を管理してから導入する。容量・取得済み・更新あり・中断再開・削除を示す。
地理院タイルやアプリ本体も完全にオフラインになるとは表示しない。

### Pixel 10 Proでの測定案

同じブラウザ・画質・明るさ・開始位置で、現行版と変更版を比較する。
冷えた端末で初回通信、キャッシュあり再訪、港から市役所への連続移動、徒歩で近景旋回、10分間の継続利用を測る。
読み込み待ち時間、中央値/P95フレーム時間、30FPS未満の継続、区画切替の停止、クラッシュ、端末の発熱感を記録する。
リモートデバッグ可能ならメモリも記録するが、取得できない数値は空欄とする。

暫定合格目標（未合意の提案）: 読み込み後のP95フレーム時間33.3ms以下、500ms超の操作停止なし、10分間でクラッシュなし。現行版自体が未達の場合は最初に原因を分ける。
未達なら解像度/DPR、同時表示する細部、影・反射、モデルとテクスチャ容量、読込並列数の順で実測して絞る。2Dへの移行手段を残す。

## 8. 小さな実装単位と完了条件

| 段階 | 作業 | 完了条件 |
|---|---|---|
| 0 | 現行版の固定・測定 | 版、比較画像、通信量を記録。Pixel未測定なら未測定と明示 |
| 1 | 一区画の建物選択 | 10件の原本ID一致、ドラッグ誤選択なし、再読込一致、近傍のみ取得 |
| 2 | 修正台帳と一棟置換 | 公開用schema検証、対象棟のみ除去、衝突更新、版不一致検出、旧版へ戻せる |
| 3 | びゅうお近景改善 | 同一視点の前後画像、徒歩/中遠景確認、予算と実機結果の記録 |
| 4 | 紹介1件と共有 | 提供内容確認済み、紹介から3Dへ移動、共有先で閲覧、魚取得ルール維持 |
| 5 | 更新運用の試行 | 3〜5件で素材受付→修正→公開→訂正を実施し、作業時間を記録 |
| 6 | 必要な拡張 | 実績に応じ地区別保存、写真モード、場所の図鑑を選ぶ |

段階1が失敗したまま全棟へ展開しない。段階2の仕組みができたら、地域紹介の試作は近景制作と独立に進められる。
公開前に、ガチャ→2D、ガチャ→3D→発見→復帰、事前保存の中断再開、旧保存の復元を変更の影響範囲に応じて確認する。

## 9. 今は増やさないもの・将来の判断点

- Unity移行: 現在は採用しない。配布の手軽さを失う移行費に見合う要件が生じた時に比較する。
- オンライン鬼ごっこ: 興味は確認済みだが未実装・未確定。サーバー費、同期、モバイル通信、運営対応を別設計する。
- 時間帯変更・自由写真モード・場所の図鑑: 候補として残す。まず街の見た目と更新手順を安定させる。
- AIによる現況の自動更新: 提案だけを作り、人が確認する。実在建物や店舗情報を推測で公開しない。
