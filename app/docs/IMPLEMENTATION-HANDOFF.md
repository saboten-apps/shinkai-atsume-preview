# 深海あつめ：探索統合の引き継ぎ（2026-11-14）

## 決定済み

- 本番：saboten-apps/shinkai-atsume。テスト公開：saboten-apps/shinkai-atsume-preview の GitHub Pages。
- ガチャが入口。探索画面を開くまで探索コードを、3Dを選ぶまでThree.js/GLBを読み込まない。
- 日付・魚・隠れ場所は全員共通。日付はJST、探索中は開始時の日付を固定する。
- 発見カードはB案（3D街並み背景）。2D探索時は事前レンダリングした3D画像を使う。
- 実機検証端末：Pixel 10 Pro。実機のFPS・メモリ・発熱は未測定。
- サーバー、協力店、店頭QR、営業・AI導入支援、来店記録は今回の範囲外。
- 共有画像に「うみまちラボ」とPLATEAU出典を入れる。

## 実装

- `src/features/exploration/` に探索のドメイン・保存・2D・3D・カードをまとめた。
- `#/explore/YYYY-MM-DD` は、その日を引いた履歴がある場合だけ探索できる。URLから引いていない魚を取得しない。
- `hidingPlaces.v1.json` は10候補。種は `SHA-256("shinkai-exploration:hide-v1:YYYY-MM-DD")` の先頭4バイトをbig endian uint32化し、配列長で剰余。ガチャの種・アルゴリズムは変更していない。
- 20m以内で発見ボタンを押す。2Dと3Dの地図表示は探索マーカー/地図中心が位置。自由飛行時は人物の位置を使い、ビーコンとの高さ差30m未満と視線の遮蔽判定も加える。
- 現段階の魚の目印は光る立体（ENU y=85）。実際の生息水深の表現ではない。
- 10地点はモデルの鉛直レイキャストで上面を確認済み。駅へ続く地点を高い建物から15mずらした。`public/map/cards/validation.json` が記録。周辺の飛行による到達性、ヒントの分かりやすさ、美観は実機で再確認する。
- 2D地図は港〜駅の模式図。背景は道路位置の正確な再現ではなく、探索座標だけは3Dと共通。実際の道案内には使わない。
- 探知音は明示操作で開始し、間隔と音程が変わる。初期OFF。方向・距離・色・文でも探索可能。
- `shinkai_exploration_v1` に日付、魚、場所、種の版、発見日時、モードだけを保存。画像は保存せず必要時に生成する。従来の図鑑キー・形式・カウントは変更しない。
- 3Dで発見直後はHUDなしのライブ描画をキャプチャ。再読込後や2Dの場合、3D街並みの読み込みが未完了の場合は各地点の固定3D背景で再生成する。完全に同じ写真の永続保存は未実装。
- 既存の魚画像には不透明な背景があるため、生成モックの切り抜き配置と異なり丸い枠に原画を収めた。
- Web Shareでファイル共有、対応外は画像保存＋文のコピー。共有をキャンセルしても発見記録は残る。
- WebGL不可・描画中断・3Dモジュール読み込み失敗で2Dに移れる。20FPS未満が継続した場合も2Dを案内（強制切替ではない）。
- 3DのDPR上限は1.5。既存の建物ストリーミング、衝突判定、地形、港〜駅の連続飛行を移植。
- 施設ごとの展示・提供メモは魚詳細で非表示にした。元の魚データは変更していない。
- MVPの「行ったよ」入力を非表示にした。旧リアクションデータは消していない。「行きたい」は端末内のみ。人数集計を予告する文言を修正。

## ソースと公開

本体リポジトリが編集元。`data/fish.json` が唯一の魚データ原本。previewの`app/`は本体の指定コミットから作るテスト用スナップショットであり、二つのJSONを手動編集しない。

previewの `scripts/sync-app-from-main.py /path/to/shinkai-atsume` でコミット済み本体を同期する。同期元コミットと魚データのSHA-256を`app/UPSTREAM.json`に記録する。previewの元のGLBは `spike-3d/public/data`、統合版のGLBは `app/public/map/data` へビルド前にコピーする。previewに同じバイナリを二重コミットしない。

本番mainへのマージはPixel確認後。previewと本番はURLパスが違っても同じoriginならlocalStorageを共有するため、テストのガチャは本番の同日履歴にも反映しうる。既存スキーマを維持している。別originのテストでは本番図鑑は見えない。公開URL自体を変更してデータ移行が必要な場合は、既存図鑑バックアップの導出・復元を使う。

## 開発・確認

```sh
npm ci
npm run build
npm test
npm run dev -- --host 127.0.0.1 --port 5180
# 別ターミナル。PlaywrightとChromiumが必要
node scripts/check-exploration.mjs
node scripts/check-exploration-3d.mjs
node scripts/generate-discovery-scenes.mjs
```

- ビルド成功。既存20＋探索5の25テスト成功。
- 2D E2E：ガチャから発見・1200×630 PNG生成・保存復元まで、図鑑不変、ガチャと2DでThree/GLBのリクエストなしを確認。
- 3D E2E：StrictModeでの起動、モデル読み込み、飛行開始終了、2Dへ切り替えてcanvas解放、WebGL context loss後の2D復帰、2D⇄3Dで探索位置の継続、3Dでの発見とライブ描画からのPNG生成を確認。
- ブラウザ検証はLinux Chromiumのソフトウェア描画。Pixelの速度の根拠にはしない。
- Viteの671KBの3Dチャンク警告は遅延ロードするチャンクについて。ガチャ初期JSは約218KB（gzip約74KB）。
- 背景生成スクリプトは開発サーバーのソースを利用する。候補点が高さ70を超える建物上ならエラーにする。公開済みhide-v1の座標・配列順は固定し、変更は新バージョンとして扱う。

## Pixel 10 Proで次に行うこと

1. Chromeの通常タブでpreviewを開き、初回（キャッシュなし）のガチャ表示と探索開始までの時間を測る。
2. 港、駅南口、港〜駅の連続飛行を各1分、合計10分試す。落下、上昇、潜水、建物との衝突を含める。
3. 「動作情報」を開きFPS、直近300フレームのp50/p95、描画・テクスチャ数を確認し「動作情報を保存」でJSONを保存。移動中も複数地点で保存する。
4. 3D⇄2Dを繰り返し、探索位置の継続、発見、カード保存、Android共有、共有キャンセル、ブラウザ再起動後の図鑑と発見復元を確認する。
5. Chromeをバックグラウンドにして復帰、通信を切った場合、長時間の発熱・タブ終了がないかを確認。

提案した目標は中央値30FPS、p95フレーム50ms以内、通常回線で探索操作可能まで8秒以内、カード生成3秒以内、10分の操作でクラッシュなし。未達ならDPRを1へ、近傍チャンク距離・写真サイズを調整。それでも重い端末には2D入口を優先する。テスト条件と実測結果を本書に追記する。

## 残るレビュー・調整

- 10地点を人が実際に探して、ヒント・地名とモデルの対応、飛行での到達、構図を確認する。レイキャストはこの体験の確認を代替しない。
- 3Dの発見操作は現状「近づく＋発見ボタン」。魚の立体や魚自体をタップする演出は改良余地あり。
- 2D模式図の見た目・細かい操作感を調整。現地の道路形状に忠実な図にする場合は簡略化した道路データを別途生成する。
- ブラウザ共有はChromiumの自動テストではOS共有画面まで確認できていない。Pixelで確認する。
- 新しい発見記録は既存図鑑JSONバックアップの対象外。別の探索用エクスポートを必要とするか判断する（既存形式を変えない）。
- 時刻を端末で変更すれば日次結果も変わる。サーバーなしの設計上、改ざん防止は対象外。
- カード背景の再生成方針、音量、暗色背景上の表示を実機で見て調整する。

## 次段階（設計のみ、実装していない）

- 写真モード：現在のキャプチャ処理を探索の達成条件から独立させ、画像生成にフレームとブランドを追加する。新しい図鑑加算はしない。
- 時間帯：`portSky`とライトのパラメータプリセットで朝・夕・夜。日次の種や場所は変えない。夜も探知表示を見やすく保つ。
- 生息水深：現行の浅い海面とENU座標に「実際の水深」を直接対応させない。沖の海底・深度レイヤーと移動の設計、対応する場所バージョンが先に必要。
- 場所図鑑：発見履歴から場所IDごとに集計する別ビュー・別キー。魚の取得回数と実際の訪問記録から独立させる。
